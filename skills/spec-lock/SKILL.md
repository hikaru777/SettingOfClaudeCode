# /spec-lock

構想を「渡せば作れる仕様書」に固める。ゴールは分量ではなく、**未決がゼロで、現物と語彙が一致していて、検収基準として機能する**こと。

- `/spec-lock <プロダクト>` … 新規に詰め切る、または既存仕様書を棚卸しして更新
- 出力は **正本1ファイル**。`~/Documents/輝/Claude Value/<プロダクト>/spec-v<n>.md`
- 詰め終わったら `/ship` に渡す（実装段）

## 絶対ルール

1. **ラベルの出所を守る**
   - `【確定】` … ユーザーが自分で決めたことだけ。AI が埋めたものを昇格させない
   - `【既定】` … AI が埋めた既定値。ディレクションでいつでも差し替え可
   - `【AI推薦】` … 本来ユーザーが決めるはずだったが、止まらないために AI が仮決めしたもの。**必ず札を付けて台帳に残し、いつでも差し替えられる形で前に出す。札の無い仮決めは捏造と同じ扱い**
   - `【不可】` … 技術的に不可能なものだけ。「リスクが高いから採らない」は【不可】ではない
   - `【未定-n】` … ユーザーの判断待ち。§未定インデックスに必ず出す
2. **一問一答で詰める**（下記「詰め方」）。「任せる」「どちらでもいい」「君の好みで」は禁句。委ねた瞬間、ユーザーの考えは動かず、仕様は前に進まない
3. **未決を本文に散らさない**。必ず §未定インデックスに集約する
4. **正本は1つ**。他の仕様書が存在するなら「参照・凍結」と明記し、**コード内コメントが指している正本パスも揃える**（不変条件）
5. **既存実装があるなら §0 現在地を最初に書く**。これが無い仕様書を渡すと、AI は現物の隣に二つ目の実装を作りにいく

## 詰め方（一問一答）

この工程の主導権は **AI が持つ**。ユーザーに「どうしますか」と広く投げるのではなく、AI が問いを立て、1問ずつ答えをもらって前に進める。

- **1ターン1問**。複数の質問を並べない
- **答えが一意に決まる粒度まで落とす**。「UI どうする？」は問いではない。「初めて来た人が最初の10秒で何を見ている状態が正解か」まで刻む
- **問いには AI の見立てと理由を1〜2行添える**。選択肢を4つ並べて選ばせない。立場を1つ示して差分で訂正させる
- **上流から順に**。その答えが他の論点を規定する順に並べる
- **答えが出たら、その場で仕様書に書き込んで【確定】に昇格させる**。溜めない
- **残り問数を常に見せる**（「あと6問」）
- ユーザーが本当に「任せる」と言った時だけ AI が決め、`【AI推薦】` で置いて台帳に残す
- 答えが前の【確定】と矛盾したら、その場で「これは §n の確定とぶつかる」と指摘してから進む

## 手順

### 0. 現在地の確定（既存実装があるなら必須・ここを飛ばさない）

- `git log --oneline -20` / ブランチ / 未コミット差分・未追跡ファイル
- スキーマ（migrations）と型定義の**実際の語彙**
- 型チェック・ビルドが通るか（Web は `npx tsc --noEmit`。dev 稼働中に build を回さない）
- 中断中の作業がないか（削除済みファイルを参照したまま／型が合わないまま止まっている等）

**必須の中身は「語彙対応表」**：

| 仕様書の呼び名 | 現物の呼び名 | ズレ |
|---|---|---|
| events | arcs | 名前のみ／列の粒度が違う 等 |

名前が違うだけで別物を作らせるのが、この工程を飛ばした時の最大の事故。

### 1. 問いの一覧を先に作る

骨を一周見て、**ユーザーにしか決められない論点だけ**を抜き出し、上流順に並べて番号を振る。技術で一意に決まるもの・慣例で埋まるものは問いにしない（AI が【既定】で埋める）。この一覧を見せてから1問ずつ始める。

### 2. 骨を埋める

1. コンセプト（表の一行 / 解く課題 / やらないこと）
2. 全体構成（サーフェスの順序、使う基盤）
3. データモデル（**現物があるなら現物の名前で書く**）
4. 処理・パイプライン（**コストが高い処理ほど後段に置き、上段で止まるほど安い**構造に）
5. 状態の規則（enum が切り替わる条件を、人の判断ではなく機械が決められる形に）
6. 外部依存とポリシー（AI・API・無料枠・支出上限）
7. UI（画面ごとに状態を網羅：empty / loading / error / 未確定 / 部分選択 / 全選択）
8. 認証・個人化
9. 課金（無料の範囲・有料の束・価格・**課金前に価値を1度体験させる導線があるか**）
10. コスト（1人時点の固定費と、1人増えるごとの追加費用）
11. これからの順序
12. 保留領域
13. 未定インデックス
14. ローンチ前チェックリスト
15. 実装の渡し方（下記 §5）

### 3. 立場別評議（部署長を立てる）

骨が埋まったら、**立場を分けて**穴を出す。1枚に兼務させない（兼務すると自分の担当の矛盾を隠す）。
**評議も自分で回さず、部署長に自分のチームを Workflow で回させる**（/ship と同じ階層）。
**立てるエージェントは全員 Sonnet 5**（`model: "sonnet"` を明示、Workflow の `agent()` にも `opts.model: 'sonnet'`）。Opus はディレクターだけ。

| 立場 | 見るもの |
|---|---|
| プロダクト | 体験の一貫性、無料/有料の線が思想と衝突していないか、誰が最初のユーザーか、**本人にしか決められない論点の洗い出し** |
| 開発 | この記述で作れるか、現物と噛み合うか、データモデルの穴、状態遷移の抜け、**実装的に無理なもの** |
| デザイン | 状態網羅、可視文字列、**実物を見て**認知が壊れる条件、この仕様で検収できるか |
| 法務・運用 | 他人の名前・画像・投稿を扱う責任、削除訂正依頼、規約、決済の前提 |
| コスト・事業 | 単価と固定費、実測で差し替える約束の期限、価格の根拠 |

評議の出力は**「A. もう決まっている（実装に流せる）／ B. 本人に上げる（3問以内）／ C. 実装的に無理・要注意／ D. 公開判断」**に仕分けさせる。仕分けずに全部投げてくるのは失敗とみなす。

各エージェントの指摘は**そのまま仕様書に入れない**。1件ずつ自分の目で検算してから反映する。

### 4. 矛盾チェック（反映後に機械的に一周）

- 【確定】同士が衝突していないか
- 無料の体験と、収集・検索・初期データの前提が衝突していないか
- 現物の語彙と仕様書の語彙が 1:1 か
- 「後で差し替える」と書いた節が、検収基準として機能しないまま残っていないか
- **コード内コメントが参照している正本パスが、今回の正本と一致しているか**（不変条件）

### 5. 渡し方の節を書く（§15 相当）

- **段階渡し**：層単位で切り、各段階の納品条件を「動くもの＋確定チェックの報告」にする
- **確定チェック文**（各指示の末尾に必ず付ける定型）：
  > 完了前に、該当セクションの【確定】項目を1つずつ引用し、実装がそれを満たしているか自己照合して報告すること。満たせない項目は勝手に代替実装せず、報告に留めること。
- **人間タスクの分離**：AI にできないもの（API 利用申請、開発者登録、キー発行と支出上限、ドメイン取得、決済アカウント審査、実カードでの決済テスト、**クレジット補充**）を先に一覧化する

## 完了条件

- 【未定】がゼロ（すべて【確定】/【既定】/【AI推薦】に落ちている）
- **【AI推薦】は全部台帳に載っていて、差し替え可能な形で見えている**
- §0 現在地（語彙対応表つき）と §15 渡し方がある
- 正本が1ファイルで、Obsidian Value に保存されている
- 現物がある場合、**その現物が今ビルドを通る状態か**を §0 に明記してある

## 更新モード（既存仕様書があるとき）

版を上げる時は、冒頭に「前版からの変更」を1〜3行で書く。変更が無い節はそのまま持ち越し、節ごと差し替えた場合は差し替えた事実を書く。**現物が仕様書から離れている間は、まず §0 を最新に直してから中身を触る**。仕様書だけ先に進めると、現物との距離が開いて渡せなくなる。
