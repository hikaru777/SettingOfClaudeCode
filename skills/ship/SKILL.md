# /ship

裁定が固まった後、**実装チームを回して「本番 push 待ちだけが残った状態」まで持っていく**ための運用。仕様を詰める段（/spec-lock）が終わってから使う。

## 完了定義

**「本番 push 待ちだけが残った状態」。** ここに到達して初めて口を開く。

- commit と**プレビュー環境へのデプロイまでは自動でやってよい**
- **本番への push だけはユーザーの「push」の一言が要る**

## 停止条件（口を開くのはこの2つだけ）

1. **本番 push 待ちになった時**
2. **ユーザーにしか決められない問いが出た時**（それも**投げっぱなしにして他を進める**。答えを待たない）

それ以外は**台帳（TaskCreate / TaskUpdate）とレポートファイル（`<repo>/.reports/`）へ書く**。進捗報告のために会話を止めない。

## 階層 — ディレクターは Workflow を回さない

★★★ **部署長を立て、部署長が自分のチームを Workflow で回す。** ディレクターが下っ端の状態管理をしない ★★★

| 役 | やること | やらないこと |
|---|---|---|
| **ディレクター**（メイン） | 采配・結果の検算・方向判断・ユーザーへの報告 | Workflow を直接回す／worker の状態管理 |
| **部署長**（dev-lead / design-lead / ops-lead …） | Workflow で worker・verifier を編成して回す。担当領域が終わるまで自走 | 自分でコードを書く／1本ごとに指示を仰ぐ |
| **worker / verifier** | 実装と検証 | commit・push・領域外のファイル |

- 部署は領域で割る（実装 / UI・情報設計 / 収集・データ品質・公開 …）。プロダクトに合わせて増減させる
- **部署間の調整は部署長同士が直接**やる（ディレクターを経由させない）
- 部署長には必ず伝える: 「1本終わるたびに報告して指示を待つ、をやってはいけない。検証で穴が出たら自分で次の Workflow を回して潰せ」

**モデルは全員 Sonnet 5（例外なし）。** 部署長も worker も verifier も `model: "sonnet"` を明示指定して立てる。部署長が回す Workflow の `agent()` にも `opts.model: 'sonnet'` を貼らせる。Opus はディレクターだけ。

## 仮決めの札

- AI が仮決めしたものには必ず **【AI推薦】** の札を付け、**台帳に残し**、いつでも差し替えられる形で前に出す
- **札の無い仮決めは捏造と同じ扱い**
- 技術で一意に決まるもの・慣例で埋まるものは札すら要らない（勝手に決めて進む）。札が要るのは「本来ユーザーが決めるはずだったが、止まらないために仮で置いた」もの

## 不変条件（「完成」と言えるのはこれが全部緑の時だけ）

- **主要 UI 部品（カード等）は全画面で1種類**＝同じ規則で描かれている
- **正本参照は常に最新版**を指している（コード内コメント・README を含む）
- 型検証・ビルドが通っている
- **部分的な達成を「完成」と呼ばない。** 不変条件込みで全緑になって初めて完成

## 絶対ルール

1. **ディレクターはコードを書かない。** 部署長も書かない。書くのは worker だけ
2. **本番 push はユーザーが「push」と言うまで実行しない**（commit・プレビューデプロイは自動可）
3. **ツール結果を捏造しない。** 1手ずつ実際の結果を見てから書く。「たぶん通った」を報告に混ぜない
4. **verifier の findings を鵜呑みにしない。** 1件ずつ再現条件・重大度を自分でトレースしてから修正指示を出す
5. **全 worker の完了前に統合検証を走らせない。** 中間状態を見た verifier は必ず FAIL を出す
6. **ユーザーが手で書いたファイル・未追跡ファイルを壊さない。** 着手前に `git status` を取り、触ってはいけない場所を明示する

## 手順

### 1. 受け入れ条件と不変条件を先に書く

- **動作**：何が見えて、何ができれば完成か
- **検証コマンド**：何が通れば合格か（下の「プラットフォーム別の掟」）
- **状態の網羅**：empty / loading / error / 未確定 / 部分選択 / 全選択
- **触ってはいけない場所**：未追跡ファイル、ユーザーが手で書いたもの、生成物
- **不変条件**：上記4つ

### 2. 台帳を作る

残りを全部 TaskCreate で外に出す。頭の中に持たない（持つから報告して確認したくなる）。各タスクに担当部署を owner で振る。

### 3. 部署長を立てて投げる

各部署長への指示に必ず含める：担当領域／絶対ルール／裁定の全文／「Workflow で自分のチームを回せ」／「公開できる状態まで自走しろ」／「上げていいのは本人にしか決められない判断だけ、それも投げっぱなしで他を進めろ」／完了時の報告先。

### 4. 部署長の報告を検算する

上がってきた数字を自分の目で確かめる（`curl` して数える、コードを読む）。鵜呑みにしない。穴があれば部署長に差し戻す（自分で直さない）。

### 5. 本番 push 待ちまで来たら、初めて口を開く

報告に含めるもの：**やったこと／通した検証の実測値／【AI推薦】の札が付いた仮決め一覧／やらなかったこととその理由／ユーザーにしか決められない問い**。

## プラットフォーム別の掟

- **Web (Next.js)**：dev 稼働中に `next build` を走らせない（`.next` が壊れて全ルート 500）。型検証は `npx tsc --noEmit`。**`tsc` が通ることは「動く」の証明にならない — 必ず `curl` で実 HTML を取って要素を数える**
- **iOS**：エージェントに `xcodebuild` を走らせない（Preview が遅延する）。scheme 名は `xcodebuild -list` で実測
- **Swift package**：`swift build --package-path` が最終ゲート
- **ファイル追加後**：XcodeGen 構成なら `xcodegen generate` を必ず実行

## worker への指示に必ず入れる文

> 触っていいのは <ファイル> だけ。それ以外は読むだけ。commit・push は絶対にしない。実装が終わったら、受け入れ条件を1つずつ引用して満たしているか自己照合して報告すること。満たせないものは勝手に代替実装せず、報告に留めること。

## verifier への指示に必ず入れる文

> コードは1行も書き換えないこと。判定は「受け入れ条件と不変条件を満たすか」だけで、好みの改善提案はしない。指摘する時は file:line と、それが実際に壊れる条件（入力・操作）を必ず添える。再現条件を書けないものは指摘しない。検証には実 HTML / 実データを見るところまで含めること。

## よく起きる事故（実例）

- **隣を巻き込む消し方**：「関連ゾーンを外す」作業で、隣にあったストリーム本体の描画ごと消えた。`tsc` は通ったまま画面が空になった → だから検証に実 HTML を必ず含める
- **計器が嘘をつく**：件数の母数が画面の実態とズレたまま「◯◯件」と表示していた → 数字を出す UI は必ず実測と突き合わせる
- **カードが2種類になる**：新しい規則を1画面にだけ入れて他を放置した → 不変条件「主要 UI 部品は全画面で1種類」で防ぐ
