# /worldview — アプリを 7層モデル × 体験→経験変換軸 の二軸で採点する

世界観の **7層モデル（縦・組成軸：境界 Threshold / 摂理 Cosmology / 住人 Inhabitants / 器 Vessel / 儀礼 Rituals / 余白 Subtraction / 集大成 Singular Voice）** に、橋野桂（Studio Zero / メタファー: ReFantazio ディレクター）の設計論「体験は即時的なもの。経験は持続的なもの。体験を経験に変えるためにアートとゲーム構造で記憶に残す設計をする」を **横・時間軸** として直交させ、二軸マトリクスでアプリを採点します。続けて 3 Phase 改善ロードマップを作成する 3 エージェント sequential チームを起動します。

7層モデルが「世界の組成」を採点するのに対し、変換軸は「世界が遊び手の中に住み着くまでの時間」を採点します。両者は併用するもので、片方だけでは世界観の全体像は見えません。

```

## 手順

### 1. アプリのパスを特定

引数があればそれを使う。なければ Bash find で候補を提示してユーザーに選ばせる：

```
find ~ -maxdepth 5 -type d -iname "{アプリ名}*" -not -path "*/.*" 2>/dev/null
```

特定すべき3つのパス：
- ソースコード（XcodeGen の `project.yml` がある場所、もしくはリポジトリルート）
- Obsidian 決定記録（`~/Documents/Obsidian Vault/Claude Value/{App}`）
- Brain agent ディレクトリ（`~/Documents/Obsidian Vault/Claude Agents Brain/{app}`）

### 2. 前提レポートの存在確認

Read で `10_world_design_synthesis.md` の存在を確認。無ければ中止。

### 3. 既存 team のクリーンアップ

別の team を leading 中なら、先に全メンバー shutdown + TeamDelete してから次へ。

### 4. team 作成 + 3 タスク作成 + 依存設定

- `TeamCreate "{app-lowercase}-7layer-audit"`
- 出力ディレクトリ作成: `mkdir -p "~/Documents/Obsidian Vault/Claude Value/世界観研究/{App}_audit/"`
- `TaskCreate` × 3:
  - task #1: 現状を 7層フレーム + 変換装置スキャン で抽出
  - task #2: 7層採点 + 二軸マトリクス採点 + 改善方針
  - task #3: 3 Phase 実装ロードマップ（変換装置の磨きカテゴリ含む）
- `TaskUpdate task#2 addBlockedBy [1]`、`TaskUpdate task#3 addBlockedBy [2]`

### 5. 3 エージェントを並行 spawn（run_in_background: true）

- **investigator**: すぐ task #1 を着手。7層スキャンに加え、即時刺激／持続記憶／両者を繋ぐ橋（変換装置）／手触り要素の所在／個別主題の候補語を抽出する
- **evaluator**: 待機中に 7層モデル 9 本のレポートを Read で予習しておく
- **roadmap-builder**: 待機中に synthesis + `project.yml` + 主要 Assembly/Coordinator を予習しておく

### 6. 進捗誘導

- investigator が task #1 完了報告 → SendMessage で evaluator に「task #2 着手」指示
- evaluator が task #2 完了報告 → SendMessage で roadmap-builder に「task #3 着手」指示
- roadmap-builder が task #3 完了 → ユーザーに最終報告

### 7. 完了処理

- 全エージェントに `shutdown_request` を SendMessage で送る
- `TeamDelete` でクリーンアップ
- `record_decision` で obsidian-brain `{app}` agent に採点結果を記録（agent が無ければ master に記録）

## 各エージェントへの共通指示（プロンプトに必ず含める）

シンジ君の master belief を遵守すること：

- **「足すな、磨け」** — 改善方針は引き算優先（引き算 ≥ 加算）
- **スコア / ランキング / 数値化 / AI 判定系は禁止**
- **表面的な実装拒絶** — BUILD SUCCEEDED は完了の証明にならない
- **美の核心は新規性** — 業界標準の機能を1つ削除する勇気
- **凡庸の対極** — 中立を装うな、敵を持て
- **人が互いの行く末を信じられる温度** — 層3 と層5 の交点
- **Wittgenstein Weltbild** — 「世界観があります」とコピーで書いた瞬間に世界観は逃げる
- **集大成は事後現象** — 集大成（層7）は事後的現象なので「直接実装する」案は出させない。「層1〜6 が透明作動する条件を整える」方向のみ許可する
- レポートは敬体（〜です・〜ます調）

加えて v2 では以下を全エージェントに徹底させる：

- 7層モデル（縦・組成軸）と「体験→経験変換軸」（横・時間軸）は直交関係にあります。両者は併用するものであり、片方だけで世界観を判定してはいけません。
- 「体験」は即時刺激、「経験」は持続記憶です。両者を繋ぐ「変換装置」の有無を見抜くのがあなたの仕事です。
- 変換軸の採点は「変換が起きているかを質的に見抜く」ためのものであり、項目を増やしたり数値化したりするためのものではありません。
- メタ・ナラティブは事後発見でよい性質を持ちます。設計時に確定させようとせず、「将来そう見える余地が殺されていないか」だけを採点します。
- 「地に足のついた要素」は単なるリアリズム志向ではありません。世界観の純度を最優先しつつ、要所に手触りを差すバランスを評価します。

## 二軸マトリクス採点尺度（evaluator 必読）

判定対象は **「変換装置が機能しているか」** です。◎ / ○ / △ / ✗ は変換装置の状態を質的に表現する記号で、点数や順位ではありません。

| 記号 | 状態 |
|---|---|
| ◎ | 変換装置が世界観の核に組み込まれ、即時と持続が両立している。装置が場当たり的でなく、層2摂理・層3住人に裏打ちされた必然として作動している |
| ○ | 変換の兆しはあるが、装置として安定していない。即時／持続のどちらかは成立しているが、もう一方が偶発的・属人的 |
| △ | 即時はあるが経験として残らない／持続はあるが即時刺激が無い、の片寄り。両立していない |
| ✗ | 変換装置が無い。loss aversion 駆動・機能羅列・凡庸装置のみで世界が住み着く時間が発生していない |

判定の手順（evaluator が必ず文章で示す）:

1. その層・その視点で **「即時刺激は何か」** を1文で書き出す
2. その層・その視点で **「持続記憶として何が残るか」** を1文で書き出す
3. **「両者を繋ぐ変換装置は何か」** を1文で特定する。特定できなければ ✗ または △ 確定
4. 装置が世界観の他層（特に層2摂理・層3住人）と連動しているかを判定 → ◎ / ○ の差分

判定の境界:

- 4問すべてに答えられた場合 → ◎
- 3問まで → ○
- 2問以下 → △
- 装置を特定できない → ✗

- **メタ・ナラティブ余地** — 個別主題の誠実さ／メタ層への伏線が殺されていないか／作者の他作品との事後発見的接続点、の3問で判定。完成形を提案してはいけない
- **総合変換** — 4視点を機械加算しない。変換装置の有無を質的にひと言で表現し、「ここに変換装置の核が育ちうる／育っていない」を1行添える

- 数値スコア・順位・合計・平均・レーダーチャートを出してはいけません
- メタ・ナラティブの完成形を提案してはいけません（事後発見性を殺すため）
- 機械的に5段階で測ってはいけません — 変換装置の有無を質的に判断してください
- loss aversion 駆動（streak 赤字常駐・期限切れ脅迫等）を「両立」と認めてはいけません
- 層4・層7 は直接採点せず、層1〜3・5・6 の整い方から間接判定します（「— 出力層」と明記し、間接判定の文章を添える）

```

## 注意事項

- 3 エージェント sequential 体制を崩さない（並行採点は判定基準が揺らぐ）
- 完了後は必ず TeamDelete でクリーンアップ
- ◎合格判定はめったに出ない。○ 部分的でも実装上は十分機能する
- 改善案で「機能を足す」案には必ず代替の「磨く / 削る」案を併記する
- belief「面白くないからやらない領域」（スコア・ランキング・数値化・AI判定）を改善方針に出すな
- AGEYO のように Achievement Page / streak / 期限切れ赤字常駐などの **loss aversion 駆動** は採点で減点対象
- 「機能を作る」ではなく「世界の法律を制定する」、「画面を磨く」ではなく「沈黙を磨く」、「ユーザーを楽にする」ではなく「世界の住人として成熟させる」 — この3つの翻訳を全エージェントに徹底させる

### v2 がやらないこと（implementer / evaluator / roadmap-builder すべてに適用）

- **採点項目を増やしません** — 横軸4視点は「変換装置を多面照射する切り口」であって、評価項目の追加ではありません
- **数値化しません** — ◎○△✗ の質的記号のみ。集計・平均・レーダーチャート禁止
- **メタ・ナラティブを設計時に確定させません** — 事後発見でよい性質を尊重します。「シリーズ全体の主題は ○○ にすべき」のような提案は禁止
- **層4・層7 を直接採点しません** — 出力層であって入力層ではありません
- **AI 判定確信度を出しません** — シンジ君のポリシー「面白くないからやらない領域」に該当します
- **3 エージェント sequential 体制を崩しません** — 並行採点は判定基準が揺らぐため禁止

### 出力に出してはいけないもの

- 数値スコア（◎=4点 などの換算）
- 順位付け（A 層 > B 層 のような比較）
- レーダーチャート・棒グラフ等の視覚化
- AI 判定確信度
- 「総合点」「平均」「達成率」
